TRANSPARENCY & DATA PROTECTION

Privacy policy.

Personal Wellbeing is an independent personal-use wellbeing project in development. This policy explains the current testing purpose and data handling of its public information website.

Last updated: 20 October 2026

1. Purpose and status

Personal Wellbeing is a private, single-owner wellbeing project. Its separate Cloudflare Worker imports selected Fitbit/Google Health and optional YAZIO records, and hosts a small personal dashboard. This GitHub Pages website is a public information and privacy-policy site only. An optional version 0.9 release adds derived, automatic habits and passwordless day-to-day access for individually paired devices.

2. Google data and permissions

During testing, the owner may explicitly authorize read-only access to Google Health activity and fitness, sleep, and health metrics or measurements. These categories include workouts, steps, sleep sessions and stages, heart rate and weight. This project does not request permission to edit or delete Google Health data.

3. How data is used

The owner authorizes read-only access to Google Health for steps, overnight sleep, daily HRV, weight and exercise summaries. The optional unofficial YAZIO module imports daily calorie and macronutrient totals. The separate private dashboard also stores morning and evening wellbeing check-ins, manual habits, daily logs and goals in Cloudflare D1. The owner can add automatic habits that calculate their status from already imported records, for example starting sleep before a specified local time, recording exercise on a given day, or crossing a specified daily calorie threshold. Configured habit rules and thresholds are stored in the private database. The automatic status is computed from the existing imported readings rather than being entered manually.

Missing or unverified readings are treated as unknown, not automatically classified as a failed habit. Personal rule-based insights compare available observations, display evidence thresholds and do not establish medical causation. No external AI processor receives health or habit records in this release. This public website does not collect private health data.

4. Storage, sharing and security

This public GitHub Pages site has no sign-in, health-data forms, advertisements or behavioral analytics; GitHub may process normal infrastructure access logs. The separate Cloudflare Worker stores configured provider health measurements, nutrition totals, sync status, check-ins, habit rules/logs and goals in the owner's EU-jurisdiction D1 database.

The existing password-based app session is protected by a short-lived signed cookie. If the owner enables the optional passwordless-device mode, each trusted phone or computer is paired once using a short-lived, single-use enrollment link generated through the owner's Cloudflare ADMIN_TOKEN. The device then receives a random, HttpOnly, Secure, SameSite=Strict cookie valid for up to one year, so opening the app normally needs no password or login screen. D1 stores only hashed device tokens and hashed one-time pairing codes, together with creation, expiry and revocation timestamps. The owner can revoke all paired devices using an ADMIN_TOKEN-protected management command. Unpaired devices cannot access the private API. The pairing link must be kept secret and expires after ten minutes or one use.

Google OAuth credentials are stored as Cloudflare Worker secrets; the optional YAZIO renewal token is encrypted with a separate Worker secret before storage in D1. Data is transferred via TLS and D1 is encrypted at rest. EU jurisdiction does not guarantee all provider or Cloudflare processing stays within the EU. The service worker caches only static app assets, not private API responses. No records are sold, used for advertising or sent to an external AI provider by this release.

5. User choice, retention and deletion

The owner controls provider permissions and may revoke Google Health authorization in Google Account connections. Provider data, habit definitions, thresholds, logs and check-ins have no automatic expiry until the owner deletes them. Archiving habits or goals retains earlier records. Revoking provider access or disabling imports does not automatically delete previously stored records. The owner can delete provider tables, health records and habit history in the private D1 Console or delete the entire database. In passwordless-device mode, individual device authorizations expire after up to one year and can be revoked earlier through an ADMIN_TOKEN-protected operation. Cloudflare infrastructure backups may have their own retention policy.

6. YAZIO API limitations

The YAZIO private API is not officially supported, published or endorsed by YAZIO. It may change, block access, or stop working at any time; using it is subject to YAZIO's terms. The project requires the owner's informed approval before connecting their account, and automatic synchronization remains off until they verify the imported nutrition figures. The module avoids repeated calls when access is blocked or rate limited.

7. Changes

This notice describes the current personal imports and optional version 0.9 automatic-habit and passwordless-device features. It will be revised before enabling external AI processing, push notifications, new data categories or new recipients.

8. Contact

For questions about the personal development project, contact the owner via the project owner's GitHub profile or the support email shown on the project's Google OAuth consent screen.
